* **Database:** PostgreSQL 16 is the application database. The backend receives only the non-superuser app-role `DATABASE_URL`; only the one-shot `migrate` service receives `MIGRATION_DATABASE_URL` with owner credentials. Pinned driver: `psycopg2-binary==2.9.9`.
* **Schema migration:** Alembic owns the schema, including asset metadata/review fields, ML score-history columns, the CVE cache and catalog, audit rows, indexes, PostgreSQL audit immutability triggers, and `findings.final_priority` / `priority_source` with deterministic legacy backfill (revision `0004_final_priority`). Revision `0005_cve_catalog` creates the indexed reference table and grants the app role SELECT only; revision `0006_user_deactivation` adds `users.is_active` for audited deactivation/reactivation. Revision `0002_audit_truncate` blocks TRUNCATE; `0003_app_constraints` refuses to migrate duplicate asset names or finding pairs, then enforces case-insensitive asset-name and `(asset_id, cve_id)` uniqueness. App grants are DML-only on application tables, SELECT/INSERT on audit logs, sequence USAGE, and no schema CREATE or DDL rights; owner default privileges preserve future grants. The `migrate` service completes Alembic before the backend starts; backend startup does not run migrations.
* **Authentication:** `/me` is available; login throttling allows five failed attempts per username/IP in 15 minutes and is process-local. Refresh tokens were deferred; PBKDF2-HMAC-SHA256 remains at 600,000 iterations.
* **Assets:** Admin/analyst create, edit, and delete are audited transactionally; assets with findings cannot be deleted. CSV host/IP lookup checks both asset name and `ip_or_domain`.
* **CVE lookup:** The prepared `data/processed/master_cves_2026-10-08.csv` is optional and not tracked. The manual `load-catalog` profile mounts it read-only only into `scripts/load_cve_catalog.py`, which streams/upserts the required fields into `cve_catalog`; startup never loads the CSV. Lookups use the cve_id unique index, then the live provider and explicit unavailability; app access is SELECT-only. Offline scans use catalog data where available. Three `DEMO_CACHE` values are illustrative, not authoritative live scores.
* **Deployment:** Compose uses PostgreSQL 16 and a named volume with private, environment-supplied credentials and distinct owner/app roles. No database host port is published by default; `docker-compose.local.yml` adds a loopback-only port for local development. Backend startup waits for PostgreSQL health and successful one-shot migration. `setup_dev.ps1` refuses to overwrite an existing `backend/.env` and runs the migration service before app-role initialization.
* **Synthetic demo:** Compose explicitly enables `SECUREVISION_DEMO_MODE`; the demo seeder uses the same configured `DATABASE_URL` as the app and never clears existing rows. The UI shows a synthetic-data badge in demo mode. Seeded ML predictions are intentionally unavailable without NVD enrichment.
* **SQLite conversion:** `scripts/sqlite_to_postgres.py` is manual-only and source-read-only. It was exercised only with a newly created synthetic source and isolated PostgreSQL targets; it preserved IDs/timestamps, copied score history/audit rows, filled legacy asset metadata, reset sequences, verified counts, and refused a nonempty rerun. * **Testing strategy:** All tests require PostgreSQL and the Compose `postgres-tests` profile; fixtures use disposable per-test PostgreSQL schemas, including migration/index, duplicate, concurrency, and audit-trigger checks. SQLite is not a test database.
* **Status vocabulary:** The operational status is `Resolved`, not `fixed`; dashboard “fixed this month” is derived from resolution audit events. This naming is preserved in the API and interface.
* **Auth deviation:** PBKDF2-HMAC-SHA256 at 600,000 iterations is retained for password-hash compatibility rather than migrating to Argon2/bcrypt; refresh tokens remain deferred and login throttling is process-local.
