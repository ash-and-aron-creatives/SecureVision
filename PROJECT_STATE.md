# Project State: SecureVision
* **Current Phase:** PostgreSQL verification blockers closed (2026-11-12); proposal-parity work has not started.
* **Status:** P5 evaluation remains a negative result. ML-assisted likelihood and risk are nullable experimental advisory fields; the deterministic 320-rule tier remains primary and unchanged.
* **Data Split:** Train: 2022-2024, Val: 2025, Test: 2026-01 to 2026-09-08 (Held-Out). Prospective Holdout running daily.
* **Label Definition:** in_cisa_kev_catalog AND (kev_date_added <= published_date + 30 days).
* **Likelihood Provider:** Deterministic scoring remains unchanged. Frozen calibrated XGBoost is an additional advisory signal using publication-time CVSS/vector/CWE/description features only; KEV and EPSS are excluded from model features.
* **ML Risk Formula:** `likelihood × exposure_factor × criticality_factor`; constants, validation-derived risk thresholds, and recommended-action templates are in `backend/rules_config.py`.
* **Model Results:** Authenticated `/model/results` and frontend Model Results screen expose only recorded evaluation data, with unavailable metrics left null/not available.
* **Database:** PostgreSQL 16 is the application database. `DATABASE_URL` uses the non-superuser runtime app role; `MIGRATION_DATABASE_URL` uses the owner/migrator role for Alembic. Pinned driver: `psycopg2-binary==2.9.9`.
* **Schema migration:** Alembic owns the schema, including asset metadata/review fields, ML score-history columns, the CVE cache, audit rows, indexes, and PostgreSQL audit immutability triggers. Revision `0002_audit_truncate` blocks TRUNCATE; `0003_app_constraints` refuses to migrate duplicate asset names or finding pairs, then enforces case-insensitive asset-name and `(asset_id, cve_id)` uniqueness. App grants are DML-only on application tables, SELECT/INSERT on audit logs, sequence USAGE, and no schema CREATE or DDL rights; owner default privileges preserve future grants. Startup runs Alembic before serving.
* **Authentication:** `/me` is available; login throttling allows five failed attempts per username/IP in 15 minutes and is process-local. Refresh tokens were deferred; PBKDF2-HMAC-SHA256 remains at 600,000 iterations.
* **Assets:** Admin/analyst create, edit, and delete are audited transactionally; assets with findings cannot be deleted. CSV host/IP lookup checks both asset name and `ip_or_domain`.
* **CVE lookup:** The prepared `data/processed/master_cves_2026-10-08.csv` is optional, lazy, and not tracked. Compose can mount a teammate-provided dated file read-only at `/data/cves/<filename>` through `CVE_DATASET_HOST_PATH` and `CVE_DATASET_FILENAME`. Without it, lookup uses PostgreSQL cache/live-provider fallbacks and reports its source or explicit failure; offline scans retain a deterministic tier and mark ML unavailable when description data is missing. Three `DEMO_CACHE` values are illustrative, not authoritative live scores.
* **Deployment:** Compose uses PostgreSQL 16 and a named volume with private, environment-supplied credentials and distinct owner/app roles. No database host port is published by default; `docker-compose.local.yml` adds a loopback-only port for local development. Backend startup waits for PostgreSQL health and migrates before serving. `setup_dev.ps1` refuses to overwrite an existing `backend/.env`.
* **Synthetic demo:** Compose explicitly enables `SECUREVISION_DEMO_MODE`; the demo seeder uses the same configured `DATABASE_URL` as the app and never clears existing rows. The UI shows a synthetic-data badge in demo mode. Seeded ML predictions are intentionally unavailable without NVD enrichment.
* **SQLite conversion:** `scripts/sqlite_to_postgres.py` is manual-only and source-read-only. It was exercised only with a newly created synthetic source and isolated PostgreSQL targets; it preserved IDs/timestamps, copied score history/audit rows, filled legacy asset metadata, reset sequences, verified counts, and refused a nonempty rerun. It is never called by routine startup.
* **Testing strategy:** Default `pytest` uses isolated temporary SQLite fixtures. The Compose `postgres-tests` profile runs the full suite against PostgreSQL using disposable per-test schemas, including migration/index, duplicate, concurrency, and audit-trigger checks.
* **Status vocabulary:** The operational status is `Resolved`, not `fixed`; dashboard “fixed this month” is derived from resolution audit events. This naming is preserved in the API and interface.
* **Auth deviation:** PBKDF2-HMAC-SHA256 at 600,000 iterations is retained for password-hash compatibility rather than migrating to Argon2/bcrypt; refresh tokens remain deferred and login throttling is process-local.
* **Blueprint limitation:** `SecureVision_Master_Blueprint` is absent from this checkout. Section 18 prompts and exact P8-P12 criteria cannot be verified verbatim; `BLUEPRINT_TRACEABILITY.md` and `docs/VIVA_NOTES.md` say so explicitly.
* **Dashboard:** Real total-assets, open-vulnerabilities, critical, and fixed-this-month values are exposed from persisted assets/findings/audit history.
* **Validation (2026-11-12):** Fast suite: 469 passed, 12 PostgreSQL-only tests skipped, 101 warnings. PostgreSQL Compose suite: 480 passed, 1 skipped, 103 warnings; the skip requires the intentionally unbundled prepared CVE CSV and was separately verified through the optional mount. Two scoped-URL test failures caused by SQLAlchemy's password-redacting `str(URL)` were fixed by rendering URLs with the password only for internal subprocess arguments; both targeted tests then passed. TypeScript, lint, build, npm audit (0 vulnerabilities), base and dataset Compose configs, and `git diff --check` passed. Isolated HTTP smoke tests, app-role permissions, real-CVE ML inference, and restart persistence passed. Alembic upgrade-twice/check/downgrade/upgrade passed. The Docker images contain no `.env`, database, or training data. The original `backend/.env` hash stayed unchanged; cleanup removed only the `sv_verify2` project and preserved the 19 pre-existing volumes and seven pre-existing containers. The scratch local frontend install hit an npm registry idle timeout; the frontend nevertheless started with the available dependency tree, and the isolated production image built and served HTTP 200.
* **Remaining risks:** The prepared CVE catalog remains external, ignored local data; uncached lookups need either that mount or network access to providers. Fresh `npm install` was not verified because the registry timed out. These do not block the database contract; proposal parity remains deliberately unstarted.
* **Next Step:** Proposal-parity work may begin only when requested; keep the deterministic scoring tier primary unless new evidence justifies a change.
